# 个人 Agent 项目开发路线（以可证明的成果验收）

## 产品原则

- **定位**：科研 Agent 是演示领域；底层仍是通用任务管理、Tool Calling、RAG、证据校验与后端工程化。
- **边界**：GPT Researcher 是上游研究引擎。个人开发的是 FastAPI 产品/API、科研流程、评价标准、证据约束及部署。
- **优化标准**：测试前后对比、失败案例、复现步骤，不只改名字/README/提示词。

## V0：现有可运行参考骨架（本压缩包内容）

- [x] 离线演示研究任务提交与状态查询
- [x] PDF 上传、数据库文档索引
- [x] 论文比较基线、PDF 页面证据核验
- [x] GPT Researcher Adapter 与可选 LLM 提取入口
- [x] 极简 UI、Dockerfile、测试
- [ ] 真实 GPT Researcher API 联调与网络/密钥测试
- [ ] 生产部署、安全审计与压测

## V1：最小真实 Agent 项目（建议优先完成）

1. 配好研究模型与检索服务，记录**10 个真实任务**的成功/失败情况。
2. PDF 源数据清洗：按页保存 page number 和 document ID。
3. 解决不同 GPU / 数据集实验表格解析不稳定问题；缺失字段返回 null 与原因。
4. 将报告中的引用逐条映射到可核查原文，建立 citation_verified / unsupported_claim 指标。
5. 将长任务从 HTTP 请求中移入可靠队列（先本地验证，再引入 Redis / RQ）。
6. 使用 Docker Compose 在**另一台电脑**按 README 启动和演示。

**验收**：输入“对比 HybridSN、SSRN、动态图 GNN 在高光谱分类中的优势与局限”，输出可用报告、来源说明和至少两篇结构化论文对照，且每个报告引用可回溯。

## V2：具备工程深度的实习项目

1. 自建 `/api/v1/tools/arxiv_search`，加入年份区间/任务主题筛选、DOI 去重、分页、限流和重试。
2. 增加论文专用检索链路：Chunk → Embedding → 向量检索 + BM25 → Reranker → 带页码答案。
3. 增加任务工作流（可用 LangGraph）：规划 → 检索 → 证据筛选 → 多论文比较 → 证据复核 → 报告；每个节点明确输入输出。
4. 为多轮任务保存 state，支持失败恢复与步骤上限；对高风险写操作加人工审批。
5. 完成自动评测集（建议 30～50 个问题）：Recall@k、引用精确率、有效数据集名称识别率、调用成功率、耗时、Token 成本。
6. 输出 ablation：纯搜索 vs 领域搜索、无重排 vs 重排、无证据核验 vs 有证据核验。

**验收**：发布指标表、实际测试集/匿名数据与测试脚本，而不是凭空写“准确率提升 30%”。

## V3：岗位匹配层（可选，不要同时追）

- Python AI 实习：LangGraph、Tool Calling、RAG Evaluation、FastAPI、Redis、PostgreSQL 优先。
- Java + AI 后端实习：加一个单独的 Spring Boot API 网关（鉴权/持久化），通过 HTTP 调 Python Agent，清晰隔离语言职责。
- 科研特色：增加高光谱论文表格解析与复杂实验条件核对；不要假称能自动复现论文代码。

## 7～14 天压缩顺序（工作量估算，不代表必能完成）

## 面试时要能够解释

- GPT Researcher 负责什么，你本人负责什么？
- Tool Calling 和固定工作流的区别？
- 为什么 PDF 出现了 OA=99% 不能证明系统抽取结果可以直接比较？
- 结构化输出 JSON 为什么还需运行时校验？
- 异常重试、超时、失败退出如何设计？
- 为什么本 Demo 的 BackgroundTasks 不适合长时大量任务？
- 你验证了哪些指标？对照方法是什么？
