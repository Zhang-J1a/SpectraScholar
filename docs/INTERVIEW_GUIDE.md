# 面试讲解与技术学习指南

> 目标：让你能独立解释每个模块、每个设计取舍，以及哪些不是自己做的。

## 1. 30 秒项目介绍

> SpectraScholar 是一个科研文献调研 Agent。通用网页搜索、抓取和报告生成使用 Apache-2.0 的 GPT Researcher；我负责的是科研业务层：把论文抽取结果绑定到 PDF 页码和原文片段，做多论文实验条件比较，只有条件一致才允许排名；再实现带页级引用的混合 RAG 和可观测的本地工作流。项目有 FastAPI 后端、中文 Web UI、SQLite 状态、Docker 配置和 61 个离线测试。真实 GPT Researcher 调用因为环境没有 Key 和外网，只完成了 Mock 集成和上游 API 签名核对，没有写成“真实联调成功”。

## 2. 2 分钟架构讲解

1. **入口**：FastAPI 单应用，`api/` 按资源拆路由；中间件加 Trace ID、限流、安全头、统一错误。
2. **两类研究**：
   - 网页/上游：`research.py` 的 `GPTResearcherBackend`，每任务独立 JSON 配置，调用 `conduct_research()` + `write_report()`，超时/重试/状态机/事件；
   - 本地：`workflow.py` 的 7 节点 DAG，处理已上传 PDF。
3. **可信层**：`evidence.py` 定义“页码→原文→值”的核验原语；`extraction/` 所有字段带 `EvidenceRef`；`citations.py` 对报告做引用审计。
4. **对比层**：`compare.py` 把指标按 `dataset|metric|train_ratio|patch_size|protocol` 分组，条件不全就不排名。
5. **RAG**：页级 chunk → BM25 + 向量 → RRF/词法重排 → 抽取式/LLM 回答 → 引用核验；空结果拒答。
6. **存储**：SQLite 短连接，任务/事件/文档/对比/工作流；报告同时落文件。
7. **前端**：原生 HTML/JS，无构建步骤；轮询任务状态，渲染报告和引用跳转。

## 3. 每个阶段重点学习的 3～5 个知识点

### P0：真实 Agent 集成

1. **Adapter 模式**：业务代码只依赖 `ResearchBackend` 协议，Demo 与 GPT Researcher 可替换。
2. **配置优先级**：库的 `Config` 可能让环境变量覆盖你的 per-run 配置；要读源码确认，而不是猜。
3. **错误分类**：可重试（超时/429/网络）与不可重试（缺 Key/缺依赖/空输出）要分开，否则会重试到天荒地老。
4. **状态机与事件**：`queued → running → completed/failed`，加 Trace ID、尝试次数、耗时、事件日志，才能定位失败。
5. **不要伪造成功**：Demo、Mock、真实联调必须在 API/报告/日志里可区分。

### P1-A：结构化抽取

1. **Pydantic 不是万能的**：它校验类型，不校验“值是否真的在论文里”；需要额外的证据层。
2. **LLM 输出必须可拒绝**：候选 + 页码 + quote，逐字核验；不匹配就丢弃并记录。
3. **缺失值语义**：`null` 不是失败，而是诚实；不要用领域常识补全。
4. **PDF 版面噪声**：标题/作者/年份是版面推断，置信度要标低；表格不是纯文本。
5. **表格结构 vs 证据**：pdfplumber 能给出“哪一行是 HybridSN、哪一列是 OA”，但数值仍需回到页文本核验；结构证明关联，文本证明存在，语义仍需人工。
6. **关联关系**：正文窗口关联只是候选；表格行列关联更强，但仍要核对多级表头/合并单元格。

### P1-B：对比与可比性

1. **“SOTA”比较的前提**：同数据集、同指标、同训练比例、同补丁、同划分协议。
2. **分组算法**：条件 key + 至少两篇文档 + 组内排名；缺失条件直接不可比。
3. **不要跨数据集排名**：OA 不是跨数据集可加的分数。
4. **报告要写边界**：即使条件一致，随机种子/评估代码仍可能不同。

### P1-C：引用核验

1. **三层区分**：页码存在 / 原文匹配 / 语义正确；本项目只自动做前两层。
2. **引用语法**：自定义 `[[doc:id p.N "quote"]]`，可解析、可校验、可点击。
3. **缺引用检测**：对含 OA/AA/Kappa 数字的句子检查同一句是否有引用。
4. **外部链接**：不联网就不要说“已验证”，标 `external_unchecked`。

### P2：RAG

1. **页级 chunk**：保留页码和字符偏移，才能引用回原文。
2. **混合检索**：BM25 擅长术语精确匹配，向量擅长语义；RRF 是简单稳健的融合。
3. **拒答**：空库/低重合时返回拒答，比让 LLM 编造更可信。
4. **embedding 的诚实标注**：hash 是词法哈希，不是语义模型；不能拿它的分数宣称语义效果。
5. **引用回验**：LLM 回答中的引用要过 `audit_report`；没有有效引用就降级为抽取式。

### P3：工作流与工程化

1. **固定 DAG vs 自主 Agent**：固定流程可测试、可追踪；自主循环需要更强的失败恢复和预算控制。
2. **节点契约**：每个节点输入/输出摘要、超时、重试、错误持久化。
3. **幂等**：`idempotency_key` 防止重复提交；失败任务重试要新建 job。
4. **SQLite 连接管理**：上下文管理器不等于关闭连接；Windows 文件锁是真实坑。
5. **部署边界**：`BackgroundTasks` 只适合本地；生产要队列、取消、预算、多租户。

## 4. 高频追问与参考回答

### Q1：GPT Researcher 负责什么？你负责什么？

上游负责：网页搜索、抓取、上下文管理、报告生成、部分多 Agent 流程。
我负责：Adapter 边界、每任务配置、任务状态/日志/重试、PDF 管理、结构化抽取、证据核验、可比性分析、引用审计、混合 RAG、工作流、API/UI/测试/部署。

**不要说**“我实现了 Deep Research Agent 的规划/搜索/报告”，那是上游。

### Q2：Tool Calling 和固定工作流有什么区别？

Tool Calling 是模型在运行时选择工具和参数，灵活但不可预测、难测试；固定工作流是开发者定义节点和顺序，可测试、可审计、成本可控。本项目本地文献流程是固定 DAG；网页研究交给上游的自主流程。未来可以只在“选择分析维度/是否重试”这类局部决策引入 LLM，而不是把整个流程交给模型。

### Q3：为什么 PDF 里出现 OA=99% 不能证明你的抽取结果可以直接比较？

因为还需要确认：哪个数据集、哪个训练比例、什么补丁、什么划分、是否同一评估代码、表格行列是否对应。本项目把这些条件作为可比组的 key；缺失就不排名。

### Q4：结构化输出 JSON 为什么还要运行时校验？

模型可能返回：非法 JSON、字段类型错误、页码越界、quote 不存在、value 不在 quote 中、把不同数据集/比例混在一起。Pydantic 只解决结构；证据层解决“是否真的在原文”；语义层仍需人工。

### Q5：怎么处理超时、429、失败？

- 每阶段/总任务超时；
- 有限次重试 + 指数/线性退避；
- 429/网络/超时可重试；缺 Key/缺依赖/空输出不可重试；
- 失败写 `error_type`、事件和耗时；
- 不把失败包装成成功；
- 外部 API 只读。

### Q6：为什么 `BackgroundTasks` 不适合生产？

它在 Web 进程内执行，无持久化队列、无跨进程重试、无取消、无并发隔离；进程重启会丢任务。生产应换 RQ/Celery + Redis，任务状态仍在 DB，worker 可横向扩展。

### Q7：为什么会话里要区分 `verified_quote` 和 `verified_page_only`？

前者证明引文文本真的在该页；后者只证明页码存在。两者可信度不同，报告和 UI 要展示差异，不能都叫“已验证”。

### Q8：hash embedding 有什么用？

它让整个 RAG 流水线在无 API Key 时可运行、可测试；但它是词法哈希，不是语义模型。真实语义质量必须用 OpenAI/sentence-transformers 重新评测。项目在 UI、README、评测文档都标注了这一点。

### Q9：为什么不用 FAISS/Milvus/pgvector？

个人 PDF 规模小，内存 + JSON 足够；接口已抽象，换存储不影响 API。一次性引入四套数据库会增加部署和调试成本，不符合第一版目标。

### Q9.5：表格解析怎么避免“读错行列”？

- pdfplumber 只处理能检测到的结构表；
- 表头必须命中 OA/AA/Kappa 别名；
- 行首作为方法名，列作为指标；
- 单元格必须是单一数值；`98.4/97.1`、`98.4 ± 0.2` 直接拒绝并记录；
- 数值必须能在页文本中定位，否则 `quote_not_found`；
- 数据集/比例/补丁/协议只从表格标题上下文提取，缺失就保持 null；
- 复杂跨页表、多级表头、图片表格不在当前能力内。

### Q10：如果给你更多时间，优先做什么？

1. 真实 API/真实论文评测（没有这个，所有质量指标都只是流水线验证）；
2. 真实 embedding + reranker 的检索消融，验证混合检索是否真的有收益；
3. 复杂表头/跨页表/OCR；
4. Redis 队列与取消/预算；
5. 多用户隔离与 PostgreSQL。

## 5. 演示脚本（3 分钟）

1. 打开页面，指出顶部徽章：`demo / heuristic / hash`，说明不会冒充真实。
2. 文献库上传 2 篇 PDF，指出 SHA 去重与页数。
3. 点击“比较选中论文”：
   - 展示 OA 可比、排名；
   - 展示 Kappa 单篇“不可比”；
   - 展示“不可比项与风险提示”；
   - 下载 Markdown。
4. 点击“运行本地工作流”：展示 7 个节点状态、耗时、证据核验。
5. 知识库索引 → 提问 → 展示页级引用；点引用打开原文页；再问一个库外问题 → 拒答。
6. 研究任务：Demo 提交 → 展示状态、事件、报告头“演示模式、不是调研结果”。
7. 任务记录：展示 Trace、耗时、失败重试入口。
8. 最后明确说：真实 GPT Researcher 需要 Key/网络；本环境只完成 Mock 集成与签名核对。

## 6. 简历写法（只写已验证事实）

**SpectraScholar｜科研文献调研与分析 Agent（个人二次开发）**

- 基于 Apache-2.0 GPT Researcher 构建 FastAPI 科研 Agent，设计 Adapter 与任务状态机，加入 Trace、超时、有限重试、错误分类与执行事件，区分 Demo 与真实模式。
- 设计 Pydantic 证据契约，把方法/数据集/OA/AA/Kappa/训练比例/图构建绑定到 PDF 页码与连续原文片段；模型候选不匹配即拒绝，缺失字段返回 null。
- 实现多论文可比性分析，以数据集、指标、训练比例、补丁尺寸、协议为分组键，条件不全不排名；生成含证据附录的 Markdown 报告。
- 实现页级混合 RAG（BM25 + 向量 + RRF + 词法重排）与拒答，回答带页级引用并做引用审计。
- 建立 61 个 pytest（覆盖 87%），包含非法 PDF、缺 Key、超时重试、幻觉引用、不可比条件、表格多值单元格等失败路径；提供三份合成夹具评测、BM25/向量/混合消融与真实论文评测模板。
- 使用 pdfplumber 解析带线 OA/AA/Kappa 表格，把行识别为方法、列识别为指标；数值仍回页文本核验，多值单元格拒绝；表格指标与正文指标去重合并。

**不要写**：

- “真实 API 联调成功”“真实论文准确率 X%”“语义检索提升 X%”“Docker 部署验证通过”——当前都没有真实证据。
- 等完成真实评测后再补数字，并注明数据集、样本量、基线、运行日期。

## 7. 面试时的“红旗”

- 把 GPT Researcher 的搜索/报告说成自己写的；
- 把 Demo 说成真实调研；
- 把 hash 检索分数说成语义效果；
- 把“原文匹配”说成“事实正确”；
- 把合成夹具 100% 说成真实论文准确率；
- 说不出失败案例和限制；
- 只讲框架名，讲不出数据流和权衡。
